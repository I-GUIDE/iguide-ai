# Version lock for reproducible builds.
#
# WHY THIS FILE EXISTS
# requirements.txt carries unbounded pins (`langchain>=1.0`, bare `pandas`, bare `numpy`),
# and both Dockerfiles run a plain `pip install -r requirements.txt`. The consequence,
# measured on 2026-08-07:
#
#   dev machine        langchain 1.2.10  core 1.4.9  langgraph 1.0.10  pandas 2.2.3  numpy 2.1.3
#   clean pip install  langchain 1.3.15  core 1.5.4  langgraph 1.2.11  pandas 3.0.5  numpy 2.5.2
#
# So the deployed image ran a *major* pandas version, and a langchain triple, that nobody
# had tested. The resolution even moved inside a single afternoon (a dry-run gave langchain
# 1.3.14; the real install an hour later gave 1.3.15). Nothing measured against "the eval
# baseline" means anything while the stack underneath it drifts silently.
#
# These are the versions the 503-passing suite and the recorded eval baseline were produced
# on. Upgrading is fine — but as a deliberate, measured step: bump here, re-run
# `pytest rag_pipeline/tests/` and `scripts/eval_retrieval.py`, and record the delta in
# docs/DEVLOG.md.
#
# Usage (both Dockerfiles and any clean venv):
#   pip install -r requirements.txt -c constraints.txt

# --- agent / LLM stack. Fastest-moving packages in the tree. -------------------
langchain==1.2.10

langgraph==1.0.10
# The langgraph SUB-PACKAGES must be pinned too, and this is not optional bookkeeping:
# with only `langgraph==1.0.10` pinned, a clean build resolved langgraph-prebuilt 1.0.13,
# which does `from langgraph.runtime import ExecutionInfo` — a name that does not exist in
# langgraph 1.0.10. The result is an ImportError raised while importing
# `langchain.agents`, i.e. create_agent dies and the ENTIRE agent is dead on arrival.
# Pinning the parent alone does not prevent that; these version independently.
